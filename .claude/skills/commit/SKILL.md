# 커밋

목표는 "변경사항을 저장하는 것"이 아니라 **나중에 이 커밋만 읽고도 왜 이렇게 바꿨는지 알 수 있게 만드는 것**이다.
git log는 코드가 답해주지 못하는 것(의도, 배경, 버린 대안)을 담는 유일한 자리다. 이 관점이 아래 모든 절차의 이유다.

## 1. 변경사항 분석

```bash
git status
git diff            # 워킹트리
git diff --staged   # 이미 스테이징된 것
git log --oneline -10
```

세 가지를 동시에 본다. 특히 **이미 스테이징된 변경이 있으면 사용자가 의도적으로 골라둔 것**이므로 함부로
`git add -A`로 덮지 않는다.

diff를 읽을 때 파일 목록만 훑지 말고 실제 hunk를 읽는다. 무엇이 바뀌었는지는 diff에 나오지만
**왜 바뀌었는지는 대화 맥락에만 있다.** 커밋 메시지의 가치는 대부분 후자에서 나오므로,
이번 세션에서 사용자가 무엇을 요청했고 어떤 문제를 겪었는지 떠올려 근거로 삼는다.

### 커밋 전 확인

diff에서 아래가 보이면 커밋을 진행하지 말고 먼저 사용자에게 알린다. 한 번 커밋되면 히스토리에서 지우기 어렵다.

- API 키, 토큰, 비밀번호, 인증서 같은 자격증명 (`.env.example`, 설정 파일, 테스트 픽스처에 실수로 들어가는 경우가 많다)
- 디버깅용 `console.log`, 주석 처리된 코드 덩어리, `TODO: 지우기`
- 의도치 않게 딸려온 대용량 파일이나 빌드 산출물

## 2. 논리적 단위로 분류

하나의 커밋은 **하나의 이유**를 가진다. "이 커밋을 되돌린다면 무엇이 함께 되돌아가야 하는가"로 판단하면 대개 명확해진다.

같이 묶는다:
- 기능 하나와 그 기능의 테스트
- 리팩터링과 그에 따른 호출부 수정
- 컴포넌트 변경과 그 때문에 고친 스타일·테스트

나눈다:
- 기능 추가와 무관한 포맷팅·오타 수정
- 성격이 다른 두 버그 수정
- 의존성 추가와 그 의존성을 쓰는 기능 (설정 변경이 큰 경우)

단위가 여러 개면 `git add <경로>`로 하나씩 스테이징해 순서대로 커밋한다.
파일 하나 안에 성격이 다른 변경이 섞여 있으면 `git add -p`를 쓴다.

무리해서 쪼개지 않아도 된다. 억지로 나눈 커밋은 각각이 빌드되지 않아 오히려 되돌리기 어려워진다.

## 3. 메시지 작성

### 형식

```
<타입>(<스코프>): <한국어 요약>

<왜 이렇게 바꾸는지 — 배경과 문제>

- <경로>: <무엇을 했는지>
- <경로>: <무엇을 했는지>
```

- **타입**: `feat` `fix` `refactor` `chore` `docs` `test`
- **스코프**: 선택. 이 저장소는 대부분 생략하고, 영향 범위가 좁고 이름이 분명할 때만 쓴다 (`chore(skills):`)
- **요약**: 한국어, 명사형 종결(`추가` `변경` `수정` `재배치`). 마침표 없음. 72자 이내
- **본문**: `~한다` 평서형. 무엇을 했는지보다 **왜**를 먼저 쓴다. diff를 읽으면 아는 내용은 반복하지 않는다
- **불릿**: 여러 파일이 얽힌 변경일 때만. 한 파일 한 줄짜리 변경에는 불필요하다

본문은 한 줄짜리 사소한 변경이면 생략해도 된다. 판단 기준은 "왜"에 설명할 게 있는가다.

### 실제 예시

이 저장소의 커밋이다. 톤과 밀도의 기준으로 삼는다.

**예시 1 — 배경 설명이 핵심인 경우**

```
chore: Gemini 생성 모델을 gemini-3.1-flash-lite로 변경

기존 gemini-2.5-flash는 free tier가 폐지되어, free tier로 제공되며 가격 대비
성능이 우수한 gemini-3.1-flash-lite로 교체한다. GA 안정 모델이고 응답 속도가
빠르며 자체 완결형 React 컴포넌트 생성 용도에 적합하다.
```

"free tier가 폐지되어"가 이 커밋의 전부다. 이건 코드 어디에도 안 남는다.

**예시 2 — 여러 파일이 얽힌 경우**

```
feat: Google 모델 실패 시 자동 폴백 추가

우선순위 모델(gemini-3.1-flash-lite)이 실패하면 gemini-3.5-flash로 폴백하도록
한다. free tier rate limit 초과나 일시 장애 시에도 생성이 이어지도록 안전망을
둔다.

- server/fallback.ts: withModelFallback 순수 고차함수. 모델을 순서대로 시도하고
  실패 시 다음으로 폴백, 모두 실패하면 마지막 에러를 던진다.
- server/index.ts: callGoogle을 callGoogleModel(네트워크)로 분리하고
  GOOGLE_MODELS 목록으로 폴백 오케스트레이션.
- server/fallback.test.ts: 성공/폴백/전체실패/빈목록 4개 테스트(RED→GREEN).
```

**예시 3 — 본문 없이 충분한 경우**

```
feat: 컴포넌트 카드에 새로고침/재생성 버튼 추가
```

### 피할 것

| 나쁨 | 좋음 | 이유 |
|---|---|---|
| `fix: 버그 수정` | `fix: 프리뷰 새로고침 시 이전 코드가 남는 문제 수정` | 무슨 버그인지 알 수 없다 |
| `chore: 코드 정리` | `refactor: 프로바이더 설정을 PROVIDER_CONFIG로 통합` | 무엇이 정리됐는지 알 수 없다 |
| `feat: App.tsx 수정` | `feat: API 키 설정을 상단바 디스클로저로 이동` | 파일명은 diff에 이미 있다 |
| `feat: 사용자가 요청한 대로 UI를 애플 스타일로 변경했습니다` | `feat: UI를 애플 디자인 언어 기반으로 재설계` | 요약은 서술문이 아니다 |

### 트레일러

세션에 커밋 속성(attribution) 지시가 주어져 있으면 그 지시를 그대로 따라 트레일러를 붙인다.
지시가 없으면 붙이지 않는다. 모델 이름을 임의로 지어내지 않는다.

## 4. 승인 후 커밋

커밋 **전에** 사용자에게 보여준다.

- 어떤 단위로 나눴는지 (여러 개면 각각 어떤 파일이 들어가는지)
- 각 커밋의 전체 메시지
- 1단계에서 걸린 게 있으면 그 내용

그리고 승인을 기다린다. 사용자가 "커밋해줘"라고 말했다는 것은 커밋이라는 **행위**를 승인한 것이지,
아직 보지 못한 **메시지**를 승인한 것이 아니다. 메시지는 남고 고치기 번거롭다.

승인을 받으면 heredoc으로 커밋한다. 여러 줄 메시지에 `-m`을 여러 번 쓰면 문단 구분이 어그러진다.

```bash
git commit -F - <<'EOF'
feat: 요약

본문 첫 문단.

- 경로: 설명
EOF
```

커밋 후 `git log --oneline -3`으로 결과를 확인하고 사용자에게 보고한다.

### 하지 않는 것

- **push하지 않는다.** 별도로 요청받았을 때만 한다. 커밋은 로컬에서 되돌릴 수 있지만 push는 남에게 보인다
- **`--no-verify`를 쓰지 않는다.** 훅이 막으면 훅이 옳다고 보고 실패 내용을 사용자에게 전한다
- **`--amend`나 리베이스로 기존 커밋을 고치지 않는다.** 명시적으로 요청받은 경우만
- **기본 브랜치에 직접 커밋하지 않는다.** `main`/`master`에 있으면 브랜치를 먼저 만들자고 제안한다
