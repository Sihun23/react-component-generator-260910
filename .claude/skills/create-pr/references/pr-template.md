# PR 본문 템플릿

이 저장소의 기존 PR(#6, #7, #9, #10)에서 공통으로 쓰인 구조다. 섹션 제목을 바꾸지 마라.
해당 사항이 없는 섹션은 비워두지 말고 **통째로 생략한다.** 빈 섹션은 리뷰어에게
"확인했는데 없음"인지 "확인 안 함"인지 알려주지 못한다.

```markdown
## 요약

이 PR이 무엇을 하는지 2~4문장. 리뷰어가 이 문단만 읽고도 무엇을 볼지 알 수 있어야 한다.
변경 목록을 요약하지 말고 **결과**를 서술한다.

## 변경 사항

- **주제**: 무엇을 어떻게 바꿨는지. 파일 경로는 근거로 인용하되 파일 목록 나열이 되지
  않도록 주제 단위로 묶는다.
- **주제**: 여러 파일이 한 목적을 위해 바뀌었으면 한 항목으로 묶는다.

## 변경 이유

왜 이 변경이 필요했는지. 어떤 문제·요청·장애에서 출발했는지 쓴다.
`## 요약`에서 이미 충분히 설명됐으면 생략한다.

## 검증

실제로 실행한 것만 적는다. 실행하지 않은 항목은 `[ ]`로 두고 무엇이 남았는지 밝힌다.

- [x] `bun run test` — N개 통과
- [x] `bun run lint` — 통과
- [x] `bun run build` — 통과
- [ ] 브라우저 스모크 테스트 (리뷰어 확인 필요)

## 체크리스트

- [x] 테스트 통과
- [x] 린트/빌드 통과
- [ ] 문서 갱신 (필요 시)
- [x] Breaking change 없음
```

## 작성 규칙

- **한국어로 쓴다.** 제목도 본문도 한국어다.
- 본문은 `~한다` 평서형. 커밋 메시지와 같은 어조다.
- **실패하거나 건너뛴 검증을 숨기지 마라.** 통과하지 못한 항목이 있으면 그 사실과 이유를
  적는다. 기존 PR #10은 실패한 테스트 14개가 이번 변경의 회귀가 아님을 별도 워크트리로
  확인한 근거까지 본문에 적었다. 그 수준을 기준으로 삼는다.
- 파일 목록을 나열하지 마라. GitHub의 Files changed 탭이 이미 보여준다. 본문은
  **왜 그렇게 묶였는지**를 설명하는 자리다.

## 제목 형식

커밋 요약과 같은 규칙을 쓴다: `<타입>: <한국어 요약>`

- 타입: `feat` `fix` `refactor` `chore` `docs` `test`
- 한국어 명사형 종결, 마침표 없음
- 커밋이 하나면 그 커밋 요약을 그대로 쓴다
- 커밋이 여럿이면 전체를 아우르는 한 줄을 새로 쓴다. 나열하지 마라

예시:
- `feat: Gemini 모델을 gemini-3.1-flash-lite로 변경 + 자동 폴백 추가`
- `chore: Vitest 기반 TDD 테스트 환경 구축`
- `feat: 반응형 미리보기 뷰와 생성 히스토리 localStorage 영속화`
