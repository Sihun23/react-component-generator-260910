# TDD Rule

> **이 규칙은 Rigid다. 상황에 맞게 변형하지 마라.**
> 판단이 필요하다고 느끼는 지점은 이미 규칙에 답이 있다. 예외를 만들고 싶으면
> 규칙을 어기지 말고 **사용자에게 물어라.**

## 1. 적용 기준

### 반드시 TDD를 적용한다

- **비즈니스 로직** — 조건 분기, 계산, 상태 전이, 정규화·변환 함수
- **API** — 요청 핸들러, 응답 형태, 에러 코드 매핑, 입력 검증
- **유틸리티** — 순수 함수 전부
- **버그 수정** — 예외 없이. **버그를 재현하는 실패 테스트를 먼저 쓴다.**
  재현 테스트 없이 고친 버그는 고쳐졌는지 알 수 없고, 재발해도 아무도 모른다

### TDD가 불필요하다

- **타입 정의** — 타입 검사기가 이미 검증한다
- **설정 파일** — `vite.config.ts`, `tsconfig.json`, `eslint.config.js` 등
- **순수 UI** — 로직 없는 마크업과 스타일. 단, **조건부 렌더링·이벤트 핸들러·폼 검증이
  들어오는 순간 비즈니스 로직이므로 적용 대상이 된다**
- **SQL 스키마·마이그레이션**

경계가 애매하면 **적용하는 쪽을 택한다.** 불필요한 테스트의 비용은 몇 분이고,
빠진 테스트의 비용은 장애다.

## 2. RED-GREEN-REFACTOR

### RED — 실패하는 테스트를 먼저 쓴다

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 담지 마라. 깨졌을 때
  무엇이 깨졌는지 즉시 알 수 있어야 한다
- **반드시 실행해서 실패를 눈으로 확인한다.** 실행하지 않은 RED는 RED가 아니다
- **실패 이유가 "기능 미구현"이어야 한다.** 오타, import 경로 오류, 문법 에러로 인한
  실패는 RED가 아니다. 실패 메시지를 읽고 원인이 미구현인지 확인하라
- 테스트 이름은 검증하는 동작을 서술한다. `test1`, `works` 금지

### GREEN — 통과시키는 최소한의 코드만 쓴다

- **테스트를 통과시키는 데 필요한 코드만 쓴다.** 그 이상은 전부 추측이다
- **YAGNI.** 지금 테스트가 요구하지 않는 확장 포인트, 옵션 파라미터, 추상화를
  만들지 마라. 필요해지면 그때 테스트가 요구할 것이다
- **신규 테스트와 기존 테스트를 모두 실행해 전부 통과하는 것을 확인한다.**
  신규만 돌리고 넘어가지 마라 — 회귀는 거기서 나온다
- 코드가 지저분해도 이 단계에서는 괜찮다. 정리는 다음 단계 몫이다

### REFACTOR — 동작을 그대로 두고 구조만 고친다

- 허용: **중복 제거, 이름 개선, 헬퍼 추출, 구조 정리**
- **매 변경마다 테스트를 다시 돌려 green을 유지한다.** red가 되면 즉시 되돌린다
- **새 동작을 추가하지 마라.** 리팩터 중에 떠오른 기능은 메모해두고 다음 사이클의
  RED로 넘긴다. 리팩터 단계에서 추가된 코드는 테스트가 없는 코드다
- 고칠 게 없으면 건너뛴다. 억지로 리팩터하지 마라

### 반복

다음 동작을 고르고 **RED로 돌아간다.** 사이클은 작게 유지한다. 한 사이클이 길어지면
동작을 너무 크게 잡은 것이다.

## 3. 삭제 강제

**테스트보다 프로덕션 코드를 먼저 썼다면, 그 코드를 삭제하고 RED부터 다시 시작한다.**

- **"참고용"으로 주석 처리해 남기는 것도 금지.** 남겨두면 그것을 통과시키는 테스트를
  쓰게 되고, 그 순간 TDD가 아니라 사후 테스트 작성이 된다. 테스트가 설계를 이끄는
  것이 목적이지, 이미 쓴 코드를 정당화하는 것이 목적이 아니다
- 다른 브랜치나 파일에 옮겨두는 것도 같은 이유로 금지
- 삭제한 코드가 아깝다고 느끼는 만큼, 그 코드가 검증되지 않았다는 뜻이다

## 4. 변명 차단

| 변명 | 반론 |
|---|---|
| "너무 단순해서 테스트 불필요" | 단순한 코드의 테스트는 30초면 쓴다. 단순하다는 판단이 틀렸을 때의 비용은 그보다 훨씬 크다. 단순하면 테스트도 단순하다 — 쓰지 않을 이유가 아니라 써야 할 이유다 |
| "나중에 추가하겠다" | 나중에 쓰는 테스트는 코드를 검증하지 않고 **코드의 현재 동작을 기록**할 뿐이다. 버그가 있어도 그대로 굳는다. 그리고 대개 나중은 오지 않는다 |
| "시간이 없다" | TDD는 디버깅 시간을 앞당겨 쓰는 것이지 추가로 쓰는 것이 아니다. 시간이 없을수록 수동으로 재현하고 확인하는 왕복이 더 비싸다 |
| "삭제하면 낭비" | 검증되지 않은 코드는 자산이 아니라 부채다. 이미 머릿속에 설계가 있으므로 다시 쓰는 데는 처음의 일부 시간만 든다. 매몰비용에 끌려가지 마라 |
| "프로토타입이다" | 프로토타입은 지워질 때만 프로토타입이다. 지울 계획이 없으면 그건 제품 코드다. 대부분의 프로토타입은 지워지지 않는다 |
| "테스트하기 어려운 구조다" | 그것이 테스트가 주는 첫 번째 피드백이다. 테스트하기 어렵다는 것은 결합도가 높다는 뜻이므로, **테스트를 포기할 것이 아니라 구조를 고쳐야 한다** |
| "외부 API 호출이라 불가능하다" | 순수 로직을 네트워크 호출에서 분리하면 순수 부분은 테스트 가능해진다. 분리 자체가 개선이다 |

## 5. 프로젝트 규칙 우선

**프로젝트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 규칙이 있으면 그것을 우선한다.**
이 파일은 프로젝트가 별도 규칙을 정해두지 않았을 때 적용되는 **기본값(fallback)이다.**

프로젝트 규칙과 이 파일이 충돌하면 프로젝트 규칙을 따르고, 충돌 사실을 사용자에게 알려라.
프로젝트 규칙이 이 파일보다 느슨하더라도 그것이 그 팀의 결정이다.

### 이 저장소에서

```bash
bun run test        # 전체 실행 — GREEN 확인은 항상 이 명령으로
bun run test:watch  # 사이클 중 감시 모드
```

vitest 대상 경로는 `src/**/*.test.{ts,tsx}`와 `server/**/*.test.ts`다(vite.config.ts).
`server/fallback.ts`와 그 테스트가 이 사이클로 추가된 예시다.
